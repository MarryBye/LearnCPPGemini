## 2. Ответ на твой вопрос из `REPORT.md`: «Как подключить уже собранный бинарник библиотеки без `.cpp`?»

Ты спросил:
> *«Конечный получатель подключает интерфейс `.hpp`, кладет рядом скомпилированный бинарник и сможет использовать наши технологии. Только не до конца понимаю, как ему подключить уже собранный бинарник?»*

На самом деле ты **уже делал это** в Уроке 1.1, когда собирал `.o` файлы! Смотри, как это работает на практике:

Допустим, мы хотим продать наш модуль `sequence_math` другой компании, но **скрыть** исходный код `sequence_math.cpp`:
1. Мы у себя компилируем `sequence_math.cpp` в объектный файл `sequence_math.o` (или упаковываем несколько `.o` файлов в файл библиотеки `libsequence_math.a` / `libsequence_math.dylib`).
2. **Удаляем** `sequence_math.cpp` и отправляем клиенту только **два файла**:
   - `sequence_math.hpp` (и `stats_types.hpp`) — текстовые заголовки для его **Компилятора**.
   - `sequence_math.o` (или `libsequence_math.a`) — готовый машинный код для его **Линкера**.
3. Клиент пишет свой `main.cpp`, делает `#include "sequence_math.hpp"` и запускает сборку, просто передавая наш готовый бинарник вместо `.cpp` файла:
   ```bash
   # Вариант А: если мы дали ему объектный файл sequence_math.o
   clang++ main.cpp stats_printer.cpp sequence_math.o -o app

   # Вариант Б: если мы упаковали код в библиотеку libsequence_math.a
   clang++ main.cpp stats_printer.cpp -L. -lsequence_math -o app
   ```
   Его компилятор берет сигнатуры из `.hpp`, а его линкер берет готовые машинные инструкции `T __Z14sum_of_squaresi` из нашего бинарника! Исходный код `.cpp` клиенту вообще не нужен. А в следующем уроке про **CMake** мы увидим, как это делается одной красивой строчкой `target_link_libraries()`.

## 3. Важное уточнение по твоему выводу в `REPORT.md` (Компилятор vs Линкер!)

В конце `REPORT.md` ты написал про ошибку `error: redefinition of 'SequenceStats'`:
> *«Препроцессор вставляет много раз одно и то же и дальше линкер не понимает с чем связывать сигнатуру, ведь реализация одна, а объявлений много выходит.»*

**Внимание, здесь важная неточность!**
До **Линкера** дело даже не дошло — упал **Компилятор** на Шаге 2 (во время компиляции `main.cpp`, еще до создания `main.o`)!
Почему?
- Обычные **объявления функций** (`long long factorial(int n);`) можно повторять в одном файле хоть 100 раз — компилятор не ругнется.
- Но `struct SequenceStats { ... };` — это не просто объявление имени, это **определение типа данных** (описание того, из каких полей и скольких байт состоит структура).
- В рамках одной единицы трансляции (`main.cpp` после работы препроцессора) тип `struct SequenceStats` может быть определен **только один раз**. Когда мы убрали `#pragma once`, препроцессор дважды вставил текст `struct SequenceStats { ... };` внутрь `main.cpp` (первый раз через `sequence_math.hpp`, второй раз через `stats_printer.hpp`). **Компилятор** увидел в одном тексте два определения структуры с одинаковым именем и сразу остановил сборку с `error: redefinition of 'SequenceStats'`.

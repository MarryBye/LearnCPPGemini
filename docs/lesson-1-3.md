## 1. Тема и цель урока

В первых двух уроках мы компилировали код из терминала и ловили ошибки с помощью флагов `-Wall -Wextra` и санитайзеров (`ASan`, `UBSan`). Но что делать, если программа **не падает**, санитайзеры молчат, а результат вычислений — неверный?

В Python или TypeScript первой реакцией часто бывает `print(x)` или `console.log(x)`. В C++ отладка через `std::cout` — плохая привычка:
1. Каждое добавление `std::cout` требует **перекомпиляции** проекта.
2. Вывод в поток меняет тайминги программы и расположение переменных на стеке (иногда баг памяти буквально *исчезает*, когда ты добавляешь `std::cout` — такие баги называют **Гейзенбагами / Heisenbugs**!).
3. Через `std::cout` ты не увидишь содержимое регистров процессора, стек вызовов в момент зависания или точный адрес переменной в памяти.

**Цель этого урока:**
- Понять, как устроены современные IDE для C++ (CLion, VS Code + `clangd`, Visual Studio, Xcode) и почему обычный текстовый автокомплит для C++ не работает.
- Разобраться, как работает нативный отладчик (**`lldb`** на macOS / **`gdb`** на Linux) и что именно делает флаг `-g` (`app.dSYM`).
- Научиться ставить точки останова (Breakpoints), шагать по коду (`step`, `next`, `finish`), инспектировать память и находить логические баги за секунды без единого `std::cout`.

## 2. Как это работает под капотом

### Почему IDE для C++ — это почти компилятор (`clangd` и `compile_commands.json`)

В TypeScript работает `tsserver`, в Python — `Pylance`/`Pyright`. Они просто читают файлы в папке проекта по путям `import`.
В C++ всё сложнее:
- Как мы узнали в Уроке 1.1, один и тот же `.cpp` файл может иметь **совершенно разный смысл** в зависимости от того, с какими флагами (`-std=c++20`, `-DMACOS`, `-I./include`) его вызвали!
- Поэтому для умного автокомплита, навигации (`Go to Definition`) и подсветки ошибок на лету в VS Code / Cursor / Neovim / CLion используется **LSP-сервер `clangd`** (часть проекта LLVM/Clang).
- Под капотом `clangd` запускает **настоящий фронтенд компилятора Clang** в фоновом режиме! А чтобы знать, с какими флагами компилируется каждый файл, система сборки (CMake, которую мы изучим через урок) генерирует специальный файл **`compile_commands.json`**.

#### Краткий гид по выбору среды разработки:
1. **VS Code / Cursor / Antigravity IDE** + расширение **`clangd`** (и расширение **CodeLLDB** для визуальной отладки):
   - *Важно*: стандартное расширение Microsoft C/C++ (`cpptools` IntelliSense) часто работает медленнее и хуже знает современный C++20/23, чем **`clangd`**. Профессионалы почти всегда ставят `clangd`.
2. **JetBrains CLion**:
   - Лучшая специализированная кроссплатформенная IDE (macOS, Linux, Windows). Из коробки интегрирует CMake, `clangd`, `lldb`/`gdb`, Valgrind и санитайзеры.
3. **Visual Studio (не VS Code!)** на Windows и **Xcode** на macOS:
   - Мощные нативные комбайны для платформозависимой разработки (DirectX/WinAPI или macOS/iOS Metal).

### Как работает отладчик (`lldb` / `gdb`) и зачем нужна папка `.dSYM`?

Когда в `task-1-2` ты скомпилировал код с флагом **`-g`**, рядом с бинарником `app` появилась папка **`app.dSYM`** (Debug Symbols). Зачем она нужна?

Вспомни Урок 1.1: после компиляции в машинном коде **больше нет имен локальных переменных**! Вместо `long long result = 1;` в бинарнике осталась только инструкция процессора `mov x8, #1` или запись по смещению `[sp, #16]`.
Флаг **`-g`** заставляет компилятор создать специальную таблицу соответствия в формате **DWARF**:
- *«Адреса инструкций с `0x100003d00` по `0x100003d40` соответствуют файлу `analytics.cpp`, строкам с 2 по 10»*.
- *«Переменная `result` типа `long long` лежит на стеке по смещению `[sp + 16]` (или в регистре `x8`)»*.

Когда ты запускаешь программу под отладчиком **`lldb ./app`** (или нажимаешь `F5` в IDE):
1. Отладчик запускает твой процесс через системный вызов ядра ОС (`ptrace`) и читает таблицы DWARF из `.dSYM`.
2. Когда ты ставишь **Breakpoint (точку останова)** на строку `analytics.cpp:6`, отладчик находит соответствующий адрес машинной инструкции в оперативной памяти и **временно подменяет байт этой инструкции** на специальную инструкцию аппаратного прерывания (`BRK` на ARM64 или `INT 3 / 0xCC` на x86_64)!
3. Как только процессор доходит до этой инструкции, ядро ОС замораживает твою программу и передает управление отладчику `lldb`.
4. В этот момент время в твоей программе остановлено: ты можешь смотреть значения любых переменных, менять их прямо в памяти и выполнять код по одной строчке!

## 3. Особенности и подводные камни (Best Practices & Gotchas)

1. **Никогда не отлаживай код, собранный с `-O2` / `-O3`, если ищешь логическую ошибку.**
   Вспомни `math_utils_optimized.s` из первого урока: оптимизатор выкидывает переменные, переставляет местами строки и разворачивает циклы. Если запустить отладчик на `-O2`, курсор будет прыгать вверх-вниз по файлу, а на попытку посмотреть переменную `result` отладчик скажет: `<variable optimized out>` (переменная уничтожена оптимизатором).
   - **Правило**: Для отладки всегда компилируй с **`-g -O0`**.
2. **Разница между `next` (`n`) и `step` (`s`) в отладчике:**
   - **`next` (`n`) / Step Over (`F10` в IDE)**: выполняет текущую строку целиком. Если на этой строке вызывается функция `safe_power(2, 5)`, отладчик выполнит её всю за один шаг и остановится на следующей строке `main`.
   - **`step` (`s`) / Step Into (`F11` в IDE)**: **заходит внутрь** вызываемой функции на этой строке!
   - *Ловушка новичка*: Если нажать `step` (`s`) на строчке `std::cout << result << '\n';`, отладчик провалится внутрь системных заголовков стандартной библиотеки `iostream`! Чтобы немедленно выпрыгнуть обратно из функции в место её вызова, используй команду **`finish`** (`Shift+F11` в IDE).
3. **На macOS `clang++ -g main.cpp -o app` сразу создает `app.dSYM`, а при раздельной компиляции (`.o` -> `app`) символы остаются в `.o` файлах.**

## 4. Примеры использования: шпаргалка по `lldb`

На твоем Mac уже установлен промышленный отладчик **`lldb`** (часть экосистемы LLVM/Xcode). Вся визуальная отладка в VS Code, CLion и Xcode под капотом просто отправляет команды в `lldb`. Умение пользоваться им напрямую из терминала спасает, когда нужно отладить сервис на удаленном сервере или в Docker-контейнере.

### Основные команды `lldb`:

| Команда (и её короткий алиас) | Что делает | Аналог в GUI IDE |
| :--- | :--- | :--- |
| `lldb ./app` | Загрузить бинарник в отладчик | Открыть Debug-сессию |
| `b main` или `b analytics.cpp:6` | Поставить Breakpoint на вход в `main` или на строку 6 файла `analytics.cpp` | Кликнуть красную точку слева от номера строки (`F9`) |
| `r` (`run`) | Запустить программу внутри отладчика | `F5` (Start Debugging) |
| `n` (`next`) | Выполнить следующую строку (**не заходя** внутрь функций) | `F10` (Step Over) |
| `s` (`step`) | Шагнуть **внутрь** функции на текущей строке | `F11` (Step Into) |
| `finish` | Довыполнить текущую функцию до `return` и вернуться на уровень выше | `Shift + F11` (Step Out) |
| `c` (`continue`) | Продолжить выполнение до следующего брейкпоинта или конца программы | `F5` (Continue) |
| `p expr` (`print`) | Вычислить и вывести значение переменной или выражения (например, `p result` или `p &result` для адреса в памяти!) | Навести мышь на переменную / окно Watch |
| `fr v` (`frame variable`) | Показать **все** локальные переменные и аргументы текущей функции | Панель Variables / Locals |
| `bt` (`backtrace`) | Показать полный стек вызовов функций (кто кого вызвал) | Панель Call Stack |
| `q` (`quit`) | Выйти из отладчика | Stop Debugging |

### 🟢 Легкий (Easy): Остановка в `main` и просмотр всех переменных

Допустим, мы скомпилировали программу `clang++ -std=c++20 -g -O0 main.cpp -o app` и запустили `lldb ./app`:
```text
(lldb) b main          # Ставим точку останова на начало функции main
(lldb) r               # Запускаем программу (она замрет на первой строчке main)
(lldb) n               # Делаем один шаг (выполняем первую строчку)
(lldb) fr v            # Выводим все локальные переменные текущего стекового фрейма!
```

### 🟡 Средний (Medium): Условный брейкпоинт (Conditional Breakpoint) в цикле

Представь цикл на $1\,000\,000$ итераций, который ломается только тогда, когда `i == 500`. Нажимать `n` 500 раз вручную безумно!
В `lldb` (и в любой IDE по правому клику на красную точку) можно поставить **условную точку останова**:
```text
(lldb) b analytics.cpp:7 -c "i == 5"
(lldb) r
```
Программа пролетит первые 5 итераций на полной скорости процессора и замрет ровно в тот момент, когда условие `i == 5` станет истинным!

---

### 🔴 Тяжелый (Hard): Наблюдение за памятью (Watchpoint) и поиск бага за 10 секунд

Иногда переменная в программе внезапно меняет значение, и ты понятия не имеешь, какая строчка кода её перезаписала.
В `lldb` можно поставить аппаратную ловушку не на строчку кода, а **на конкретный адрес в оперативной памяти (Watchpoint)**:
```text
(lldb) w set var result
```
Процессор на аппаратном уровне начнет следить за этими 4 или 8 байтами в ОЗУ. Как только **любая** инструкция в программе изменит значение переменной `result`, отладчик мгновенно остановит выполнение и покажет виновника!

## 5. Где это применяется в реальном мире

1. **Посмертный анализ падений на продакшене (Core Dumps / Crash Dumps)**:
   Когда высоконагруженный C++ сервер или игра у игрока падает, ОС сохраняет снимок оперативной памяти и регистров процесса в момент смерти — файл `core` (или `.dmp`). Инженер открывает этот дамп в `lldb`/`gdb` (`lldb ./server -c core.1234`), пишет `bt` и `fr v`, и видит точное состояние всех переменных и стека вызовов за миллисекунду до аварии!
2. **Отладка без исходников и оптимизация**:
   Через команду `disassemble` в `lldb` разработчики движков смотрят, какие именно машинные инструкции сейчас исполняет процессор и что лежит в регистрах `x0`–`x30`.

Мы продолжаем развивать наш вычислительный модуль. Код ниже компилируется с `-std=c++20 -Wall -Wextra -Wpedantic -Werror` **без единого предупреждения** и проходит все проверки `ASan` и `UBSan` **без единого падения**!
Однако в нем спрятаны **3 логических бага**, из-за которых обе функции возвращают неверный результат.

### Условие задачи
Создай директорию `tasks/task-1-3/` и помести туда два файла:

**`tasks/task-1-3/sequence.cpp` (с логическими багами):**
```cpp
// Функция 1: Считает сумму квадратов чисел от 1 до n включительно:
// Например, для n = 3 должно быть: 1^2 + 2^2 + 3^2 = 1 + 4 + 9 = 14.
long long sum_of_squares(int n) {
    if (n <= 0) {
        return 0;
    }
    long long total = 0;
    for (int i = 1; i < n; ++i) {
        total = i * i;
    }
    return total;
}

// Функция 2: Считает факториал числа n (1 * 2 * ... * n), при n <= 1 возвращает 1.
// Например, для n = 5 должно быть: 120.
long long factorial(int n) {
    if (n <= 1) {
        return 1;
    }
    long long result = 0;
    for (int i = 2; i <= n; ++i) {
        result *= i;
    }
    return result;
}
```

**`tasks/task-1-3/main.cpp`:**
```cpp
#include <iostream>

long long sum_of_squares(int n);
long long factorial(int n);

int main() {
    auto squares = sum_of_squares(4); // Ожидаем: 1 + 4 + 9 + 16 = 30
    auto fact = factorial(5);         // Ожидаем: 120

    std::cout << "Sum of squares (4): " << squares << '\n';
    std::cout << "Factorial (5): " << fact << '\n';
    return 0;
}
```

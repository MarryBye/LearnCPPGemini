# Урок 1.1: Как работает C++ — от исходного кода до машинных инструкций

---

## 1. Тема и цель урока

Добро пожаловать в первый урок! Прежде чем писать сложные алгоритмы или работать с памятью, нужно понять фундаментальное отличие C++ от Python и TypeScript.

Когда ты запускаешь скрипт `python main.py` или `node index.js`, твой исходный код читает **программа-посредник** (интерпретатор CPython или движок V8 с JIT-компилятором). Процессор твоего компьютера (Apple Silicon ARM64 или Intel/AMD x86_64) **не понимает** ни Python, ни JavaScript, ни даже C++. Процессор понимает только **машинный код** — бинарные инструкции конкретной архитектуры процессора и операционной системы.

**Цель этого урока:**
- Понять, почему в C++ нет виртуальной машины в рантайме и как текстовый файл `.cpp` превращается в нативный исполняемый бинарник.
- Детально разобрать **4 этапа сборки** (Препроцессинг, Компиляция, Ассемблирование, Линковка).
- Научиться отличать **ошибку компиляции** от **ошибки компоновки (линковки)** — это то, на чем спотыкаются 90% разработчиков, пришедших из интерпретируемых языков.

## 2. Как это работает под капотом

### Сравнение: Python / TypeScript (V8) vs C++

| Характеристика | Python (CPython) | TypeScript / JS (Node.js V8) | C++ (Clang / GCC / MSVC) |
| :--- | :--- | :--- | :--- |
| **Что происходит до запуска?** | Ничего (или компиляция в байткод `.pyc`). | TS стирает типы -> получается JS. | **Полная AOT-компиляция** (Ahead-Of-Time) в машинный код. |
| **Кто исполняет код?** | Виртуальная машина CPython (огромный `switch-case` цикл, написанный на C). | ВМ V8 (интерпретатор Ignition + JIT-компилятор TurboFan, написанные на C++). | **Напрямую аппаратный процессор (CPU)** под управлением ОС. |
| **Типизация в рантайме** | Динамическая (каждое число — это тяжелый объект `PyObject` в куче). | Динамическая (типы TS исчезают, в рантайме V8 угадывает типы через Hidden Classes). | **Статическая, типы стерты в машинные инструкции** (в рантайме нет понятия «типа `int`», есть только 4 байта в регистре процессора). |

### Четыре всадника сборки C++ (Build Pipeline)

Когда ты вызываешь команду вроде `clang++ main.cpp -o app`, на самом деле запускается **драйвер компилятора**, который последовательно вызывает 4 разных инструмента:

```
[ main.cpp ] 
     │
     ▼  1. Препроцессор (Preprocessor) — clang++ -E
[ main.i ]   (Чистый C++ код без #include, #define и комментариев)
     │
     ▼  2. Компилятор (Compiler) — clang++ -S
[ main.s ]   (Код на языке Ассемблера под конкретный CPU: arm64 / x86_64)
     │
     ▼  3. Ассемблер (Assembler) — clang++ -c
[ main.o ]   (Объектный файл: машинный код с «дырками» вместо внешних адресов)
     │
     ▼  4. Компоновщик / Линкер (Linker) — ld / lld
[   app   ]  (Готовый исполняемый файл Mach-O на macOS / ELF на Linux / PE на Windows)
```

Разберем каждый шаг подробно:

#### Шаг 1: Препроцессор (Preprocessor)
Препроцессор **не знает синтаксиса C++**. Это тупой текстовый редактор, который пробегает по файлу до компилятора и ищет строки, начинающиеся с решетки `#` (директивы препроцессора):
- `#include <iostream>` — препроцессор буквально находит файл `iostream` на диске, **копирует все его 30 000+ строк кода** и вставляет их вместо этой одной строчки! (В отличие от `import` в Python/TS, это не загрузка модуля в рантайме, это буквальный Copy-Paste текста до компиляции).
- `#define MAX_USERS 100` — находит в тексте все слова `MAX_USERS` и заменяет их на `100`.
- `#ifdef / #ifndef / #endif` — вырезает куски текста по условию (например, оставляет код только для macOS и удаляет код для Windows).
- Удаляет все комментарии (`//` и `/* ... */`).

Результат работы препроцессора (файл `.cpp` со всеми вставленными `#include`) называется **Единицей трансляции (Translation Unit)**.

#### Шаг 2: Компилятор (Compiler)
На вход подается раздутая единица трансляции (часто на десятки тысяч строк после `#include`). Компилятор:
1. Строит **AST (Абстрактное синтаксическое дерево)** и проверяет синтаксис и строгую систему типов. Если ты попытался сложить строку с числом или забыл `;` — **ошибка компиляции** вылетит именно здесь.
2. Переводит AST во внутреннее промежуточное представление (**IR — Intermediate Representation**, например LLVM IR в Clang).
3. **Оптимизирует код**: выбрасывает мертвый код, вычисляет константы заранее, разворачивает циклы, подставляет маленькие функции напрямую (inlining).
4. Генерирует текстовый файл на языке **Ассемблера** (`.s`) с инструкциями для твоего процессора (например, `mov`, `add`, `bl`, `ret`).

#### Шаг 3: Ассемблер (Assembler)
Переводит человекочитаемые инструкции ассемблера (`add w0, w0, #1`) один-в-один в бинарные машинные коды (`0x00040011`) и упаковывает их в **Объектный файл** (`.o` на macOS/Linux или `.obj` на Windows).
> **Важно**: каждый `.cpp` файл в проекте компилируется **независимо** в свой собственный `.o` файл! Если в `main.cpp` вызывается функция `calculate()`, которая написана в другом файле `math.cpp`, то внутри `main.o` компилятор оставляет «закладку» (неопределенный символ): *«Здесь должен быть вызов функции `calculate`, но я пока не знаю, по какому адресу в памяти она лежит»*.

#### Шаг 4: Компоновщик / Линкер (Linker)
Линкер берет все объектные файлы твоего проекта (`main.o`, `math.o`), а также скомпилированную стандартную библиотеку C++ (`libc++` / `libstdc++`, где живет реализация `std::cout`), склеивает их воедино и **разрешает ссылки на символы**:
- Он смотрит на каждую «закладку» в `main.o`, находит реальный адрес функции в `math.o` или в стандартной библиотеке и прописывает этот адрес в машинный код.
- Если ты объявил функцию, вызвал её, но забыл написать её тело (или не передал нужный `.o` файл линкеру) — ты получишь знаменитую **ошибку линковки**: `Undefined symbols for architecture...` (macOS) или `undefined reference to...` (Linux).

## 3. Особенности и подводные камни (Best Practices & Gotchas)

1. **Макросы `#define` — это текстовая мина замедленного действия.**
   Так как препроцессор просто заменяет текст, он не соблюдает ни области видимости, ни приоритеты операций, ни типы. В современном C++ вместо `#define` для констант используют `constexpr`, а для функций — обычные или `constexpr` функции (об этом поговорим совсем скоро).
2. **Объявление (Declaration) vs Определение (Definition).**
   - **Объявление** говорит *компилятору*: «Такая функция существует, вот её имя, аргументы и тип возврата: `int add(int a, int b);`». Компилятору этого достаточно, чтобы сгенерировать `.o` файл!
   - **Определение** говорит *линкеру*: «Вот само тело и машинный код этой функции: `int add(int a, int b) { return a + b; }`».
   - **Правило одного определения (ODR — One Definition Rule)**: в программе может быть сколько угодно объявлений функции, но ровно **одно** её определение во всех объектных файлах. Если определить одну и ту же обычную функцию в двух `.cpp` файлах — линкер упадет с ошибкой `duplicate symbol`!
3. **Искажение имен (Name Mangling).**
   В отличие от языка C (и Python/JS), в C++ могут существовать две функции с одинаковым именем, но разными типами аргументов: `void print(int)` и `void print(double)`. Чтобы линкер не сошел с ума от двух одинаковых имен `print`, компилятор C++ зашифровывает типы аргументов прямо в техническое имя функции в таблице символов (например, `_Z5printi` для `int` и `_Z5printd` для `double`).

## 4. Примеры использования

### 🟢 Легкий (Easy): Минимальная программа и ручной прогон по 4 стадиям

Вот классический минимальный файл `hello.cpp`:

```cpp
#include <iostream>

int main() {
    std::cout << "Hello from native C++!\n";
    return 0;
}
```

Если в терминале выполнить команды по шагам, можно увидеть изнанку каждой фазы:
```bash
# 1. Только препроцессор: посмотри, во что превращаются 6 строк кода!
clang++ -E hello.cpp -o hello.i
wc -l hello.i   # Спойлер: там будет больше 30 000 строк!

# 2. Только компиляция в ассемблер:
clang++ -S hello.cpp -o hello.s

# 3. Компиляция + ассемблирование в объектный файл (без линковки):
clang++ -c hello.cpp -o hello.o

# 4. Финальная линковка объектного файла в исполняемый бинарник:
clang++ hello.o -o hello_app
./hello_app
```

### 🟡 Средний (Medium): Как общаются Компилятор и Линкер (Declaration vs Definition)

Допустим, у нас есть файл `main.cpp`, в котором мы **объявляем** функцию `compute_tax`, но её реализацию пишем в другом файле (или забываем написать вообще):

```cpp
#include <iostream>

// Объявление (Declaration): обещаем компилятору, что где-то существует такая функция
int compute_tax(int income, int rate_percent);

int main() {
    int result = compute_tax(1000, 15);
    std::cout << "Tax: " << result << "\n";
    return 0;
}
```

Если мы выполним `clang++ -c main.cpp -o main.o` (шаги 1–3, **без линковки**):
- Компиляция пройдет **успешно без единой ошибки**! Компилятор поверил нашему обещанию.
- Если мы заглянем внутрь таблицы символов объектного файла через утилиту `nm main.o`, мы увидим:
  - `T _main` (`T` = символ определен в секции кода Text).
  - `U __Z11compute_taxii` (`U` = **Undefined**, адрес неизвестен, ждет линкера! Обрати внимание на Name Mangling: `11` — длина имени `compute_tax`, а `ii` на конце означает два аргумента типа `int`, `int`).

А вот если теперь запустить финальную сборку `clang++ main.o -o app` без тела функции — упадет **Linker (`ld`)**:
```text
Undefined symbols for architecture arm64:
  "compute_tax(int, int)", referenced from:
      _main in main.o
ld: symbol(s) not found for architecture arm64
```

Стоит нам добавить определение функции (в этот же файл или скомпилировать второй файл `tax.cpp` в `tax.o` и передать оба файла `clang++ main.o tax.o -o app`), как линкер свяжет `U` из `main.o` с `T` из `tax.o`, и программа соберется!

### 🔴 Тяжелый (Hard): Коварство препроцессора и мощь оптимизатора компилятора

Посмотрим на два тонких момента: почему препроцессор опасен и как оптимизатор компилятора (`-O2` / `-O3`) уничтожает лишнюю работу еще до запуска программы.

```cpp
#include <iostream>

// ОПАСНЫЙ МАКРОС ПРЕПРОЦЕССОРА:
#define BAD_SQUARE(x) x * x

// БЕЗОПАСНАЯ ФУНКЦИЯ КОМПИЛЯТОРА:
int safe_square(int x) {
    return x * x;
}

int main() {
    // 1. Ловушка препроцессора:
    // Мы ожидаем (3 + 2) * (3 + 2) = 25.
    // Но препроцессор тупо подставит текст: 3 + 2 * 3 + 2 = 3 + 6 + 2 = 11!
    int a = BAD_SQUARE(3 + 2);

    // 2. А функция работает как положено: вычисляет 3 + 2 = 5, затем 5 * 5 = 25.
    int b = safe_square(3 + 2);

    std::cout << "Macro result: " << a << "\n";
    std::cout << "Function result: " << b << "\n";
    return 0;
}
```

**А что под капотом в ассемблере?**
В Python или JS без оптимизаций вызов функции `safe_square(3 + 2)` в рантайме реально создавал бы кадр стека, передавал аргумент и умножал числа.
Но если скомпилировать этот C++ код с флагом оптимизации `clang++ -O2 -S`:
- Компилятор C++ увидит, что `3 + 2` известно на этапе компиляции.
- Он **сам вычислит** `safe_square(5)` прямо во время компиляции и подставит в машинный код готовое число `25`! Вызова функции `safe_square` в итоговом бинарнике даже не будет — в рантайме программа потратит **0 тактов процессора** на математику.

## 5. Где это применяется в реальном мире

1. **Движки Python и JS, которыми ты пользуешься каждый день**:
   - Когда в Python ты ставишь библиотеку вроде `numpy`, `pydantic` (до Rust-версии) или `pytorch`, внутри `pip` часто лежат предскомпилированные `.so`/`.dylib`/`.pyd` файлы — это скомпилированные C/C++ объектные библиотеки, которые загружаются в память процесса Python через динамический линкер ОС.
   - Когда в Node.js падает нативный аддон с ошибкой `dlopen(...): symbol not found`, ты видишь ошибку **динамического линкера ОС** — ровно ту же таблицу символов, которую мы разобрали выше.
2. **Ускорение сборки гигантских проектов (Unreal Engine, Chromium)**:
   - В проектах на десятки миллионов строк кода самый долгий этап — парсинг огромных `#include` в каждой единице трансляции и финальная линковка гигабайтов `.o` файлов. Понимание того, как работают единицы трансляции, позволяет инженерам ускорять сборку в десятки раз (предкомпилированные заголовки PCH, Forward Declarations, быстрые линкеры вроде `lld` и `mold`).
3. **Реверс-инжиниринг, безопасность и профилирование**:
   - Умение читать таблицу символов (`nm`, `objdump`) и сгенерированный ассемблер (`-S`, сайт *Compiler Explorer / godbolt.org*) — главный инструмент C++ разработчика, когда нужно понять: «А действительно ли компилятор соптимизировал мой цикл, или тут осталась лишняя работа?».

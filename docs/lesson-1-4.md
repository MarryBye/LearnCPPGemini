# Урок 1.4: Анатомия C++ проекта — Заголовочные файлы (`.h` / `.hpp`), единицы трансляции (`.cpp`) и защита от множественного включения

## 1. Тема и цель урока

В первых трех задачах (`task-1-1` — `task-1-3`), чтобы вызвать функцию из другого `.cpp` файла, мы вручную копировали её объявление (`long long safe_power(int base, int exp);`) в начало `main.cpp`.

А теперь представь реальный проект:
- У тебя 50 функций в математическом модуле, и они вызываются в 100 разных `.cpp` файлах.
- Если ты вручную напишешь объявления этих функций в каждом из 100 файлов, а завтра решишь поменять тип параметра с `int` на `long long` — тебе придется вручную искать и править 100 файлов! А если в одном из них забудешь — в `task-1-2` ты уже видел, что произойдет: несовпадение mangled-имен или еще хуже.

В Python или TypeScript ты просто пишешь `export function foo()` и `import { foo } from './math'`. В классическом C++ эту роль выполняет разделение кода на **Заголовочные файлы (`.h` / `.hpp` — интерфейс)** и **Файлы реализации (`.cpp` — код)** в связке с директивой `#include`.

**Цель этого урока:**
- Понять, зачем в C++ код делится на `.hpp` (или `.h`) и `.cpp` и что именно должно лежать в каждом из них.
- Увидеть, как разделение на заголовки и единицы трансляции защищает от ошибок несовпадения сигнатур и ускоряет пересборку больших проектов.
- Разобраться с классической проблемой **множественного включения заголовочных файлов** и двумя способами её решения: **`#pragma once`** и **Include Guards (`#ifndef / #define / #endif`)**.

## 2. Как это работает под капотом

### Контракт между `.hpp` (Интерфейс) и `.cpp` (Реализация)

Вспомним Урок 1.1: препроцессор при виде `#include "math_utils.hpp"` просто берет текст из `math_utils.hpp` и вставляет его в `.cpp` файл.

Как этим пользуются C++ архитекторы?
Мы выносим **все объявления (Declarations)** модуля в один файл — например, `sequence.hpp`:
```cpp
// sequence.hpp — только витрина (объявления сигнатур)!
#pragma once

long long sum_of_squares(int n);
long long factorial(int n);
```

А **определения (Definitions — тела функций)** пишем в `sequence.cpp`, при этом **в самом `sequence.cpp` тоже делаем `#include "sequence.hpp"`**!
```cpp
// sequence.cpp — реализация
#include "sequence.hpp"

long long sum_of_squares(int n) { /* ... */ }
long long factorial(int n) { /* ... */ }
```

И в `main.cpp` тоже просто подключаем заголовок:
```cpp
// main.cpp
#include <iostream>
#include "sequence.hpp" // Препроцессор сам вставит сюда актуальные объявления!
```

> **Зачем подключать `sequence.hpp` внутрь самого `sequence.cpp`?**
> Это важнейший архитектурный прием! Если ты вдруг изменишь сигнатуру функции в `sequence.cpp`, но забудешь обновить `sequence.hpp`, компилятор при сборке `sequence.cpp` увидит в одной единице трансляции два разных объявления (или заметит, что обещанная в `.hpp` функция не реализована) и сразу поможет локализовать расхождение. Кроме того, если в `.hpp` объявлены структуры или константы модуля, они сразу становятся доступны внутри `.cpp`.

---

### Разница между `#include <...>` и `#include "..."`

Ты наверняка заметил два вида кавычек в `#include`:
1. **`#include <iostream>` (угловые скобки)** — говорит препроцессору искать файл **только в системных директориях** стандартной библиотеки и внешних установленных библиотек (например, `/Library/Developer/CommandLineTools/SDKs/...`).
2. **`#include "sequence.hpp"` (двойные кавычки)** — говорит препроцессору сначала искать файл **в текущей папке твоего проекта** (рядом с компилируемым файлом или по путям флага `-I`), и только если не нашел — идти в системные папки.

*(Кстати, расширения `.h` и `.hpp` технически работают одинаково. `.h` — историческое расширение из языка C, используемое и в C++, а `.hpp` явно подчеркивает, что внутри чистый C++ заголовок. В современном C++ можно встретить оба варианта, но важно придерживаться одного стиля внутри проекта).*

---

### Почему нельзя писать тела обычных функций прямо в `.hpp`?

Представь, что новичок решил: *«Зачем мне `.cpp` файлы? Напишу-ка я само тело функции `int add(int a, int b) { return a + b; }` прямо внутри `math.hpp`!»*

Что произойдет, если этот `math.hpp` подключат через `#include "math.hpp"` сразу в двух файлах — `main.cpp` и `analytics.cpp`?
1. Препроцессор вставит тело `add` в `main.cpp` -> компилятор создаст `main.o` с символом **`T __Z3addii`**.
2. Препроцессор вставит тело `add` в `analytics.cpp` -> компилятор создаст `analytics.o` с точно таким же символом **`T __Z3addii`**.
3. На этапе линковки (`clang++ main.o analytics.o`) **Линкер взорвется с ошибкой нарушения ODR (One Definition Rule)**: `duplicate symbol '__Z3addii'`!

**Именно поэтому:**
- В `.hpp` кладут **объявления (declarations)** функций, определения типов (`struct`, `class`, `enum`) и константы/`constexpr` (у типов и констант нет конфликта секций `T` при линковке).
- В `.cpp` кладут **определения (definitions)** — исполняемый код функций.

### Проблема «Ромбовидного `#include`» и зачем нужны `#pragma once` / Include Guards

А что если в `.hpp` лежит определение структуры данных `struct Config { int max_users; };` (а структуры обязаны быть определены в `.hpp`, чтобы компилятор знал их размер в байтах!), и у нас такая цепочка заголовков:
- `config.hpp` определяет `struct Config`.
- `database.hpp` делает `#include "config.hpp"`.
- `server.hpp` делает `#include "config.hpp"`.
- `main.cpp` подключает и `#include "database.hpp"`, и `#include "server.hpp"`.

Что сделает тупой препроцессор без защиты?
Он вставит текст `config.hpp` в `main.cpp` **ДВА РАЗА ПОДРЯД** (первый раз через `database.hpp`, второй раз через `server.hpp`)!
Когда компилятор начнет читать `main.cpp`, он увидит два определения `struct Config` в одном и том же файле и мгновенно упадет с ошибкой компиляции:
`error: redefinition of 'Config'`!

Чтобы заголовочный файл вставлялся в одну единицу трансляции (`.cpp`) **строго один раз**, сколько бы раз на него ни наткнулся `#include`, в начале каждого `.h` / `.hpp` файла ставят защиту:

#### Способ 1 (Современный де-факто стандарт): `#pragma once`
Пишется одной строчкой в самом верху любого `.hpp` файла:
```cpp
#pragma once

struct Config {
    int max_users;
};
```
Компилятор запоминает файл на диске и при повторном `#include` в рамках одного `.cpp` просто игнорирует его. Коротко, чисто, невозможно опечататься в имени макроса. Поддерживается всеми компиляторами (Clang, GCC, MSVC).

#### Способ 2 (Классический по стандарту ISO): Include Guards (`#ifndef`)
Использует условную компиляцию препроцессора:
```cpp
#ifndef PROJECT_CONFIG_HPP // Если макрос PROJECT_CONFIG_HPP еще НЕ определен...
#define PROJECT_CONFIG_HPP // ...определяем его и читаем файл дальше!

struct Config {
    int max_users;
};

#endif // PROJECT_CONFIG_HPP (При втором #include макрос уже определен, и весь текст пропускается!)
```
*Тебе обязательно нужно знать оба способа: в своих проектах пиши `#pragma once`, но когда будешь читать исходники стандартной библиотеки или крупных open-source библиотек, там часто встречаются `#ifndef` гарды (или оба сразу).*

## 3. Особенности и подводные камни (Best Practices & Gotchas)

1. **Никогда не делай `#include "file.cpp"`!**
   Подключать через `#include` можно **только заголовочные файлы (`.h` / `.hpp`)**. Если сделать `#include "math.cpp"`, ты сломаешь раздельную компиляцию и получишь `duplicate symbol` от линкера.
2. **Не подключай лишние заголовки в `.hpp`, если они нужны только в `.cpp`.**
   Помни про 59 484 строки из `#include <iostream>` в `task-1-1`! Если твоей функции `long long factorial(int n);` в `sequence.hpp` не нужен `iostream` для объявления сигнатуры — **не пиши `#include <iostream>` в `.hpp`!** Подключай тяжелые библиотеки только в том `.cpp`, где они реально вызываются.
3. **Каждый `.hpp` файл обязан начинаться с `#pragma once` (или Include Guard) без исключений.**
   В продакшене отсутствие `#pragma once` в заголовке — это автоматический разворот на код-ревью.

## 4. Примеры использования

### 🟢 Легкий (Easy): Правильная пара `.hpp` + `.cpp`

**`math_ops.hpp`:**
```cpp
#pragma once

int clamp_value(int value, int min_val, int max_val);
```

**`math_ops.cpp`:**
```cpp
#include "math_ops.hpp"

int clamp_value(int value, int min_val, int max_val) {
    if (value < min_val) return min_val;
    if (value > max_val) return max_val;
    return value;
}
```

---

### 🟡 Средний (Medium): Переиспользование структуры в нескольких заголовках благодаря `#pragma once`

Представь три заголовочных файла, которые зависят друг от друга:

**`types.hpp`:**
```cpp
#pragma once

struct MetricsSummary {
    long long min_val;
    long long max_val;
    long long total_sum;
};
```

**`analyzer.hpp`:**
```cpp
#pragma once
#include "types.hpp" // Первое включение types.hpp

MetricsSummary analyze_range(int start, int end);
```

**`printer.hpp`:**
```cpp
#pragma once
#include "types.hpp" // Второе включение types.hpp

void print_summary(MetricsSummary summary);
```

**`main.cpp`:**
```cpp
#include "analyzer.hpp" // Внутри себя тянет types.hpp
#include "printer.hpp"  // Тоже тянет types.hpp — но благодаря #pragma once ошибки redefinition НЕТ!

int main() {
    auto summary = analyze_range(1, 10);
    print_summary(summary);
    return 0;
}
```

### 🔴 Тяжелый (Hard): Инкрементальная сборка (почему разделение экономит часы жизни)

Представь проект из 100 файлов `.cpp`, где сборка каждого файла занимает 2 секунды (итого 200 секунд на весь проект).
Ты исправил баг внутри тела функции в `analyzer.cpp`, **не меняя** заголовочный файл `analyzer.hpp`.
Что нужно пересобрать, чтобы получить новый бинарник `app`?
- Нужно ли перекомпилировать остальные 99 `.cpp` файлов? **НЕТ!** Ведь их `.o` файлы зависят только от объявлений в `.hpp`, которые не изменились!
- Достаточно перекомпилировать **только один** `analyzer.cpp -> analyzer.o` (за 2 секунды) и за 0.1 секунды слинковать старые 99 `.o` файлов с новым `analyzer.o`!
Именно на этом принципе работает система сборки **CMake + Ninja/Make**, к которой мы перейдем уже в следующем Уроке 1.5!

## 5. Где это применяется в реальном мире

1. **Закрытые коммерческие SDK (Игровые движки, банковские библиотеки, драйверы)**:
   Когда компания продает библиотеку (например, физический движок NVIDIA PhysX или аудиодвижок FMOD), она не хочет отдавать конкурентам свой исходный код `.cpp`. Что она поставляет клиентам?
   Она отдает **заголовочные файлы `.hpp`** (чтобы твой компилятор знал названия функций и структур) + **скомпилированный бинарник библиотеки `.dylib` / `.so` / `.lib`** (чтобы твой линкер связал вызовы)!
2. **Ускорение компиляции в крупных кодовых базах**:
   Грамотная гигиена заголовочных файлов (минимизация `#include` внутри `.hpp`) — ключевой навык C++ архитектора, определяющий, собирается ли проект за 10 секунд или за 40 минут.
